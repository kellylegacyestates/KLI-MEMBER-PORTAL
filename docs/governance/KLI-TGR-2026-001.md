## 1. Executive summary

The Kelly Legacy Institute Member Portal is intended to provide a durable institutional environment for member identity, controlled access, educational resources, publications, and governance records. Its technical design must preserve the distinction between identity proof, membership standing, institutional role, and authorization.

The verified implementation is a Next.js application using Firebase Authentication, Firestore, Firebase Admin session cookies, server-side route guards, and Firebase App Hosting configuration. Material controls exist for member profiles, membership-state enforcement, role-based administration, protected profile fields, session revocation, and selected audit events.

The implementation is not yet evidence of a complete institutional control environment. Production deployment, Firebase Console settings, provider enablement, monitoring, alerting, backup, recovery, retention, and detailed branch-protection policy require evidence outside the repository. Audit coverage is limited, the administrative audit page is presently descriptive rather than an operational viewer, and CI does not execute the existing test suite.

## 4. Institutional governance principles

### 4.1 Record before assertion — GOVERNING PRINCIPLE

Institutional claims must identify their evidence, scope, verification date, and unresolved dependencies.

### 4.2 Verification before adoption — GOVERNING PRINCIPLE

A proposed architecture does not become an operating control merely because it appears in documentation or source control.

### 4.3 Deny by default — GOVERNING PRINCIPLE

Unknown identities, unresolved profiles, inactive accounts, inactive memberships, and unrecognized roles must not receive protected access.

### 4.4 Separation of identity and authority — GOVERNING PRINCIPLE

Authentication establishes an identity. Firestore-backed institutional records establish standing and role. Neither condition alone authorizes protected access.

### 4.5 Least privilege and controlled elevation — GOVERNING PRINCIPLE

New accounts must receive the least-privileged role and may not self-assign administrative or institutional authority. Privilege changes require a trusted administrative path and an auditable reason.

### 4.6 Server-side enforcement — GOVERNING PRINCIPLE

Client-side presentation controls may improve user experience but are not an authorization boundary. Protected content and privileged mutations require trusted server-side enforcement.

### 4.7 Evidence preservation — GOVERNING PRINCIPLE

Security-relevant administrative actions should produce append-only records protected from browser modification. Retention and recovery requirements must be formally established before the audit record is treated as durable institutional evidence.

## 5. Verified application architecture

### 5.1 Framework — CURRENT — VERIFIED

The application uses Next.js 16.2.11, React 19.2.4, and TypeScript 5 with strict type checking. The App Router is implemented under `src/app`, including pages and route handlers. `next.config.ts` uses the default Next.js configuration without additional headers, rewrites, or build controls. Node.js 22 and pnpm 10.28.1 are declared.

The repository build command is `next build`; linting uses ESLint; tests use Vitest.

### 5.2 Application structure — CURRENT — VERIFIED

The application combines:

- React Server Components for protected pages and server route guards;
- client components for Firebase browser authentication and profile interaction;
- Next.js route handlers for session and privileged administrative operations;
- Firebase Admin SDK access for trusted session validation and server-side Firestore operations; and
- Firestore client SDK access for permitted self-service profile operations.

Historical Supabase and Vercel material remains in root documentation and is not evidence of the current implementation.

## 6. Secure digital identity

### 6.1 Firebase Authentication integration — IN DEVELOPMENT

The browser integration initializes Firebase Authentication from `NEXT_PUBLIC_FIREBASE_*` configuration. Email/password sign-in is implemented with `signInWithEmailAndPassword`. Registration uses `createUserWithEmailAndPassword`. Password recovery uses `sendPasswordResetEmail` and avoids account enumeration in the success message.

Repository code does not prove that the email/password provider, authorized domains, password policy, abuse controls, or email templates are configured in Firebase. Those items require external console verification.

### 6.2 Email verification — IN DEVELOPMENT

The session endpoint refuses to create a trusted session unless the Firebase ID token reports a verified email address. The registration flow does not send a verification email, and the repository contains no resend-verification operation. The verified-email requirement is therefore implemented, but the member onboarding path is incomplete.

### 6.3 Trusted server session — CURRENT — VERIFIED

After browser authentication, the application sends a Firebase ID token to a same-origin route handler. The server:

- validates request origin;
- applies a Firestore-backed rate limit of ten requests per five-minute client window;
- verifies the ID token with revocation checking;
- requires verified email and recent sign-in;
- creates a five-day Firebase Admin session cookie; and
- sets an HTTP-only, SameSite `Lax` cookie that is secure in production.

Server authorization verifies the session cookie with revocation checking. Logout and all-device revocation paths are implemented.

## 7. Member profile and access governance

### 7.1 Authoritative profile record — CURRENT — VERIFIED

The implemented member profile is stored at `users/{uid}` in Firestore. The document ID and stored `uid` map to the Firebase Authentication UID.

Verified fields are:

- `uid`
- `email`
- `displayName`
- `institution`
- `membershipPurpose`
- `role`
- `accountStatus`
- `membershipStatus`
- `createdAt`
- `updatedAt`

No subscription tier, access tier, payment status, or generalized entitlement field is implemented in this profile schema. Such attributes must not be asserted as current.

### 7.2 Profile creation — CURRENT — VERIFIED

Registration first creates the Firebase Authentication identity and then creates the corresponding Firestore profile. The profile creation function fixes initial values to:

- `role: "member"`
- `accountStatus: "active"`
- `membershipStatus: "pending"`

If profile creation fails, deletion of the newly created authentication identity is attempted as a rollback.

### 7.3 Roles and statuses — CURRENT — VERIFIED

Implemented roles are `member`, `instructor`, `executive`, and `admin`. `instructor` is defined but has no dedicated authoring authority in the present implementation. `executive` grants executive-route access; `admin` grants administrative access.

Implemented account states are `active`, `suspended`, and `revoked`. Implemented membership states are `pending`, `active`, `suspended`, `expired`, and `revoked`.

Administrative access requires a valid server session, a resolvable profile, active account status, and the Firestore `admin` role. It does not use a Firebase custom claim for role authority. There are no separate content-administrator and system-administrator roles.

### 7.4 Privilege administration — CURRENT — VERIFIED

An administrative route can update `role`, `accountStatus`, and `membershipStatus` after server-side administrator and origin checks. The profile update and audit event are committed in one Firestore transaction. Access-reducing changes trigger refresh-token revocation. A provisioning script can promote pre-existing, email-verified Firebase identities by UID; it does not create identities or passwords.

## 8. Protected routes and authorization states

### 8.1 Server route guards — CURRENT — VERIFIED

Protected member, executive, and administrative pages use server components that resolve authorization before returning protected children. The authorization model distinguishes:

1. **unresolved/loading** — client authentication and profile state remains loading until both are resolved;
2. **authenticated and authorized** — a valid session and required Firestore profile state permit access; and
3. **unauthenticated or unauthorized** — unauthenticated requests redirect to sign-in, while missing profiles, inactive status, or insufficient roles render denial states.

The request proxy performs only a coarse session-cookie-presence check. Trusted authorization remains in the server guards and privileged route handlers.

### 8.2 Protected-content flash — CURRENT — VERIFIED

At the verified commit, protected page content is nested inside asynchronous server route guards, so denied requests do not receive the guarded content. No protected-content flash path was identified in the inspected protected pages. The unused client `ProtectedRoute` component is not relied upon as the security boundary.

This conclusion covers repository structure, not an independent runtime penetration test.

## 9. Firestore data protection

### 9.1 Rules baseline — CURRENT — VERIFIED

`firebase.json` associates the default Firestore database with `firestore.rules`. The rules include a final recursive deny for unmatched documents.

For `users/{uid}`, browser access is restricted to:

- self-read;
- self-create with matching UID and fixed least-privileged authorization values;
- self-update limited to `displayName`, `institution`, `membershipPurpose`, and `updatedAt`; and
- no client delete.

Protected identity and authorization fields must remain unchanged during member updates.

### 9.2 Administrative and institutional collections — CURRENT — VERIFIED

The `isAdmin` rules helper requires an authenticated UID with an existing profile whose role is `admin` and account status is `active`. `auditEvents` denies all browser reads and writes. `publications` permits public reads only for explicit public visibility and otherwise limits access and writes to active administrators.

### 9.3 Validation depth — IN DEVELOPMENT

The rules protect ownership and privilege fields but do not comprehensively constrain profile field types, lengths, allowed-key sets on create, or timestamp semantics. Automated Firestore Rules tests and a rules-deployment workflow are not present.

Repository configuration proves the intended rules source, not that the inspected rules are deployed. Deployment status requires external Firebase verification.

## 10. Delivery and change control

### 10.1 Continuous integration — IN DEVELOPMENT

The repository CI workflow runs for pushes to `main` and pull requests targeting `main`. It checks out source, configures pnpm and Node.js 22, performs a frozen-lockfile install, builds, and lints.

The repository has a Vitest suite, but CI does not run `pnpm test`. No deployment workflow is committed. The GitHub API reported `main` as protected on August 16, 2026, but the detailed required-review and required-check policy was not inspected and must not be inferred.

### 10.2 Deployment — IN DEVELOPMENT

`firebase.json`, `.firebaserc`, and `apphosting.yaml` define a Firebase App Hosting backend and Cloud Run runtime settings. The configuration contains browser-visible Firebase Web SDK identifiers and prefers Application Default Credentials for server administration.

No repository evidence proves that the backend is deployed, that a production domain is routed, or that a deployment trigger is active. These assertions require external console verification.

## 11. Environment and secret governance

### 11.1 Repository controls — CURRENT — VERIFIED

`.gitignore` excludes `.env*` while permitting the placeholder-only `.env.example`. Firebase local state, debug logs, and PEM files are ignored. Firebase Admin values are server-only and documented as Application Default Credentials or Secret Manager bindings.

The inspected repository contains Firebase Web SDK configuration in `apphosting.yaml`. These client identifiers are browser-visible configuration, not privileged Firebase Admin credentials. No privileged private key or service-account credential was identified in tracked source during this verification.

### 11.2 Environment separation — IN DEVELOPMENT

The repository references a production Firebase project directly in App Hosting and Firebase project configuration. A documented promotion model, separate non-production project mapping, credential rotation procedure, and environment ownership register are not present.

## 12. Audit, monitoring, backup, and retention

### 12.1 Application audit events — IN DEVELOPMENT

Server code appends selected events to `auditEvents` for:

- member all-device session revocation;
- administrator session revocation; and
- authorization changes.

Browser access is denied. The administrative audit page does not query or display those records and instead presents static descriptions. Login events, ordinary logout, protected-route access decisions, content changes, and broader administrative activity are not comprehensively audited.

### 12.2 Monitoring and alerting — PROPOSED

The repository contains console diagnostics for selected authentication and administrative failures. It does not establish an operational monitoring provider, alert rules, escalation ownership, service-level objectives, or incident-response integration.

### 12.3 Backup and recovery — PROPOSED

No Firestore backup configuration, recovery runbook, recovery test, recovery-point objective, or recovery-time objective is established by repository evidence. Existing Supabase backup statements are historical and do not apply to the verified Firestore implementation.

### 12.4 Data retention — PROPOSED

No retention schedule, audit-event retention rule, profile deletion process, legal-hold control, or TTL policy is established in the repository.

## 13. Institutional knowledge infrastructure

### 13.1 Publications registry — IN DEVELOPMENT

The top-level `publications` collection, public publication routes, server-side data-access layer, validation, administrative mutations, and rules are implemented. This is an initial institutional-record capability, not evidence that all curriculum, member progress, briefings, bookmarks, or content-management features are backed by durable data.

### 13.2 Future knowledge controls — FUTURE

Versioned curriculum records, member learning history, formal records schedules, preservation exports, taxonomy governance, and institutional search remain future controls unless separately verified.

## 14. Required control roadmap

### Before broader member access — PROPOSED

1. Complete email-verification delivery and recovery paths.
2. Run the existing test suite in CI and add Firestore Rules tests.
3. Verify production Authentication, Firestore Rules, App Hosting, authorized domains, and session behavior externally.
4. Establish operational monitoring, alerting, backup, recovery, and data-retention controls.
5. Reconcile public-facing and root architecture documentation with the implemented Firebase architecture.
6. Define audit scope and provide a controlled method to review audit records.

### Subsequent hardening — FUTURE

1. Define stronger authentication and administrative assurance requirements, including MFA evaluation.
2. Establish environment promotion and separation controls.
3. Define entitlement or tier schema only when institutional policy requires it.
4. Extend audit coverage to other security and content-governance events.
5. Conduct periodic access recertification and recovery exercises.
